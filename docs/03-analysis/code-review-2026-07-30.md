## Major

### M-1. 승인번호 중복이 서버에서 막히지 않았다
`server/routes/invoices.js` — `POST /import/commit`

중복 판정이 **업로드 화면에만** 있었다. 서버는 화면이 보낸 `action`을 그대로 신뢰해서,
같은 payload가 다시 오면(요청 재시도, 중복 제출, 사용자가 '전체 새로 등록'을 고른 경우)
같은 세금계산서를 두 벌 만들었다. 화면 문구로는 "같은 파일을 다시 올려도 두 번 쌓이지 않아요"라고
약속하고 있었으므로, 그 약속이 클라이언트 판단에만 의존한 상태였다.

- 재현: 테스트 파일(208건)을 커밋한 뒤 같은 payload를 다시 보내니 **207건이 중복 생성**됨.
- 수정: insert 직전 `nts_confirm_no` 존재를 확인하고 건너뛴다. 건너뛴 수를 `dupSkipped`로
  돌려주고 결과 화면에 표시한다(조용히 넘기지 않는다).
- 근거: 승인번호는 국세청이 부여한 유일값이므로, 같은 번호의 청구서가 둘 존재하는 것은 항상 잘못이다.
- 재검증: 재업로드 시 `inserted=0 / dupSkipped=207`, 청구서 수 불변, 같은 승인번호 중복 0건.

### M-2. 놓친 회차 일괄 등록에 행 잠금이 없었다
`server/routes/recurring.js`, `server/routes/recurring-invoices.js` — `POST /issue-missed`

건별 발행(`/:id/issue`)은 `FOR UPDATE`로 규칙 행을 잠그는데, 일괄 경로에는 없었다.
두 요청이 겹치면 양쪽이 같은 `last_generated`를 읽어 **같은 회차를 두 벌** 만든다.

- 수정: 두 라우트 모두 `WHERE r.active = 1 FOR UPDATE`.
  (`FOR UPDATE OF r`로 좁히지 않았다 — MariaDB 버전에 따라 지원이 갈린다)
- 재검증: `Promise.all`로 동시 실행 → 한쪽만 생성, 같은 회차 중복 0건.

### M-3. 컬럼 매핑을 바꿔도 행별 처리가 남아 있었다
`src/lib/components/ImportWizard.jsx`

`overrides`(행별 건너뛰기/덮어쓰기)는 **행 순번**으로 저장되는데, 매핑을 바꾸면 행 자체가 달라질 수 있다.
이번에 도입한 `groupRows`(승인번호로 여러 행을 한 계산서로 묶기) 때문에 **묶는 기준 컬럼을 바꾸면
행 개수와 순서가 변한다**. 그러면 A건에 지정한 '건너뛰기'가 B건에 적용된다 — 조용히 잘못 등록된다.

- 수정: 매핑 변경 시 `overrides`를 비운다.
- 파급: 거래처·기준정보 임포트에도 같은 안전장치가 적용된다(그쪽은 행 수가 안 변해 무해했음).

## Minor

### m-1. 순서 강제 규칙이 화면에 없었다
`src/lib/components/RecurringCycles.jsx`

서버는 그 규칙의 **가장 이른 미처리 회차**만 허용한다(앞선 회차를 건너뛰면 그 앞이 영영 안 뜨므로).
그런데 화면은 놓친 회차 8건 모두에 버튼을 활성 상태로 보여줘서, 눌러본 뒤 409 에러로만 알 수 있었다.

- 수정: 규칙별 가장 이른 회차 외에는 버튼을 비활성화하고 "앞선 회차부터"를 함께 표시.

### m-2. 날짜 비교가 프로젝트 규약과 달랐다
`src/lib/components/RecurringCycles.jsx`

`new Date(new Date().toDateString())` — 비표준 파싱에 의존하고, `ui.jsx`가 명시한 규약
(`localToday()` + `T00:00:00`으로 로컬 자정끼리 비교)과 어긋났다.

- 수정: `localToday()` 기준으로 통일.

### m-3. 오해를 부르는 두 곳
`src/screens/Master.jsx`

- **첫 회차 미리보기가 수정 모드에서 틀린다**: 하한은 '그 규칙의 등록일'인데 화면은 '오늘'로 계산한다.
  옛 규칙을 열면 실제와 다른 첫 회차가 나온다 → 수정 모드에서는 계산하지 않고 안내 문구로 대체.
- **동작하지 않는 계약 배지**: 기준정보 탭 안에서는 이동 수단(`goRoute`)이 없어 눌러도 아무 일이 없었다
  → 이동 수단이 없으면 버튼이 아니라 표시(span)로 렌더(`ContractBadge` 공용화).

## 확인했으나 문제가 아니었던 것

거짓 양성을 남겨두면 다음 사람이 같은 의심을 반복하므로 기록한다.

| 의심 | 확인 결과 |
|---|---|
| 품목 상세 파일에서 승인번호를 매핑하지 않으면 금액이 이중계상되나 | 아니다. `matchKey` 폴백(구분+거래처+작성일자+합계)이 파일 내 중복으로 잡아 기본 건너뛰기 |
| 208건을 한 트랜잭션에 넣는 게 버티나 | 실측 **311ms**(건당 1.5ms). 문제 없음 |
| `contractId`가 프런트에 안 실려 계약/일반 구분이 조용히 깨지나 | `api.getRecurringExpenses`가 이미 매핑하고 있었다 |
| `useRecurringCycles`의 API 선택 객체가 stale closure를 만드나 | `kind`에만 의존하고 api 함수는 안정적이라 무해 |

## 남은 권고 (미수정 — 근거 포함)

1. **`invoices.nts_confirm_no` UNIQUE 인덱스**: DB 차원에서 못 박는 게 가장 확실하지만,
   운영 DB에 기존 행이 어떤 상태인지 확인 전이고 이 저장소엔 인덱스 헬퍼가 없다.
   앱 레벨 검사(M-1)로 먼저 막고, 배포 후 실데이터를 확인한 뒤 별도 단계로 진행하는 것이 안전하다.
2. **파서 상한(5,000행)에서 품목이 잘릴 수 있음**: 한 계산서의 품목 일부만 들어올 수 있다.
   현재 경고는 "앞쪽 N행만 읽었다"까지다. 품목 포함 파일에서 계산서 단위로 자르도록 다듬을 여지.
3. **정기 회차를 홈·사이드바에 노출**: 관리 화면은 생겼지만 화면을 열지 않으면 여전히 모른다.
   다음 작업으로 '놓친 회차 N건' 배지.
