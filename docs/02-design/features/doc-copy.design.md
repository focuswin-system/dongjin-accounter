# 3b단계 — 문서 복사(구매품의서·지급결의서) 설계

계획: `01-plan/features/simplify-2026h2.plan.md` · 앞 단계: `cash-menu-restructure.design.md`(3단계)

## 사용자 구상 (2026-09-15)

> 품의·결의서는 거래처 옆 버튼으로 과거 문서 복사 / 문서에서 복사 생성.

매달 같은 곳에 같은 품목을 사는 회사는 품의서·결의서를 매번 처음부터 적는다(소모품·임차·용역).
알찬회계의 '전표 복사'처럼 **지난 문서를 본떠 새로 쓰게** 한다.

## 확정된 결정 (계획서, 2026-09-15)

- 복사는 **연결 정보(원본 품의·지출 거래·세금계산서)·승인 상태·날짜를 복사하지 않는다.**
  연결을 복사하면 같은 청구서·지출에 문서가 둘 붙어 같은 돈이 두 번 결재된다(서버도 막지만 막히기 전에 안 만든다).

## 지금 상태 (코드 실측 2026-09-18)

- 두 문서 모두 새로 만들 때 **"어디서 만들까요?"** 선택창이 있다(SourceChooser).
  - 구매품의서: 견적요청서 · 받은 청구서 · 거래내역 · 품목 · 직접 작성
  - 지급결의서: 받은 청구서 · 구매품의서 · 이미 나간 돈 · 직접 작성
- 서버 등록(`POST /api/purchase-reqs`, `POST /api/resolutions`)은 `source` 가 없으면 **연결 없는 새 문서**로 만든다.
  → 복사는 서버 변경 없이, 화면이 **옮길 칸만** 담아 '직접 작성' 폼을 채워 여는 것으로 된다.

## 결정

### 1. 입구 셋 — 한 규칙

| 입구 | 어디 | 동작 |
|---|---|---|
| 선택창의 **"지난 문서에서 복사"** | 새 문서 → 어디서 만들까요? | 지난 문서 목록(최근순·거래처 검색) → 하나 고르면 채워진 작성 폼 |
| 문서 미리보기의 **[복사]** | 목록에서 문서를 연 머리 | 그 문서로 채워진 작성 폼 |
| 작성 폼 거래처 옆 **"지난 문서 N건"** | 거래처를 고른 직후 | 그 거래처의 지난 문서 목록 → 고르면 품목·목적을 채운다(거래처는 그대로) |

세 입구 모두 **같은 함수 하나**(`src/lib/docCopy.js copySeedOf(kind, doc)`)로 채울 값을 만든다.

### 2. 옮기는 것 / 안 옮기는 것

| 문서 | 옮긴다 | 안 옮긴다 |
|---|---|---|
| 구매품의서 | 거래처 · 제목 · 목적 · 납기 조건 · 품목(이름·규격·단위·수량·단가·비고) · 비고 | 문서번호 · 작성일/요청일(오늘로) · 신청자(지금 사람) · 결재선·승인 상태 · 연결(견적·청구서·지출) |
| 지급결의서 | 거래처 · 제목 · 지급 방법 · 품목 · 비고 | 문서번호 · 지급일(비움) · 신청자 · 결재선·상태 · 연결(청구서·품의·지출) |

- 결재선은 회사 기본 결재선으로 새로 선다(서버 `defaultApproval` — 지금과 같다).
- 품목 단가는 **지난 값 그대로** 가져오고 그 자리에서 고친다(바뀌었으면 고치는 게 한 번이다).

### 3. 목록

- 지난 문서 목록은 **반려·삭제된 것도 포함**한다 — 반려된 품의를 고쳐 다시 올리는 게 흔한 일이다. 상태 뱃지를 달아 보인다.
- 최근순 50건, 거래처·제목 검색. 문서 목록 API(`pagedList`)를 그대로 쓴다.

## 안 하는 것

- 여러 문서를 한 번에 복사하지 않는다(매달 여러 건이면 그건 반복거래의 일이다).
- 정산내역서·견적요청서는 이번에 넣지 않는다 — 사용자 구상이 품의·결의서였고, 정산은 매번 내역이 다르다.
- 서버에 '복사' 엔드포인트를 만들지 않는다. 옮길 칸을 서버가 정하면 화면과 두 벌이 된다 — 화면이 '직접 작성'과 같은 길로 보낸다.

## 복잡도 점검

- 새 개념: 없음(복사 = 채워진 '직접 작성').
- 새 입구: 선택창 한 줄, 미리보기 버튼 하나, 거래처 옆 한 줄. 셋이 같은 함수를 쓴다.

## 시나리오

1. 구매품의서 → 새 품의서 → "지난 품의서에서 복사" → 고르면 작성 폼에 거래처·품목·목적이 차 있고 날짜는 오늘, 결재는 새로.
2. 저장한 품의서에 원본의 청구서·지출 연결이 **없다**(원본이 청구서에서 만든 품의여도).
3. 품의서 미리보기 [복사] → 같은 결과.
4. 새 품의서(직접 작성)에서 거래처를 고르면 "지난 품의서 N건" → 고르면 품목만 채워지고 거래처는 그대로.
5. 지급결의서도 1~4와 같다. 지급일은 비어 있다.
6. 반려된 문서도 목록에 뜨고 복사된다.

## 검증 기록 (2026-09-18, 로컬 `repeat` 테넌트)

원본으로 **받은 청구서에서 만든 구매품의서**(청구서 연결 있음)와 품목 2줄짜리 지급결의서를 두고 확인했다.

1. 구매품의서 → 새 구매품의서 → "지난 품의서에서 복사" → 원본 선택 → 작성 폼에 건명·지급조건·비고·품목(단가)이 차고,
   요청일은 오늘, 실단가 칸은 비어 있다. 저장한 GM-2026-0003 은 **청구서 연결 없음**(원본 둘은 있음), 결재 새로.
2. 품의서 미리보기 [복사] → 같은 결과. 작성 중 도구줄에 "청소용역 지난 품의서 N건에서 품목 가져오기" → 고르면 품목만 들어온다.
3. 지급결의서 → "지난 결의서에서 복사" → 서랍에 품목 2줄·합계 280,000원, **지급일 비움**. 저장한 DJ-2026-0003 은
   금액 280,000(품목 합), 지급일 null, 청구서·품의·지출 연결 없음, 상태 작성. 미리보기 [복사]·거래처 옆 가져오기도 같다.
4. `server/test/docCopy.test.js` — 연결·결재·상태·날짜·번호·신청자·**새로 생길 모르는 칸**이 안 옮겨지는지.

### 구현하며 정한 것
- 결의서 '직접 작성' 서랍은 한 줄짜리(금액 하나)였다. 복사해 온 품목은 **목록과 합계로 보여 주고** 금액은 그 합으로 둔다.
  품목을 고치려면 만든 뒤 상세에서 편집(서랍을 표 편집기로 키우지 않았다). "품목 없이 금액만 적기"로 되돌릴 수 있다.
- 품의서 새 문서 미리보기는 seed 가 바뀔 때마다 다시 그린다 — 작성 중 다른 출처로 또 만들면 옛 폼이 남던 자리(기존에도 있던 틈).
