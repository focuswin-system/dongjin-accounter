# 전자결재 — 설계 초안

> 작성 2026-09-28 · 상태: **1단계 구현(로컬, 미커밋)** — 전결·후결·정산내역서까지 포함 · 관련: `dongjin-custom-module.design.md` D1
> 방침(사용자): 전자결재는 **회계 쪽에서 제대로 만들고, MES 를 여기에 통일**한다(사용자가 두 쪽 유지보수).

## 0. 한 줄 요약

지금 회계에 있는 것은 **종이 결재를 인쇄해 주는 결재란**과 누구나 누르는 '승인' 스위치뿐이다.
결재자·차례·반려·상신·결재함·결재 이력이 없다. 문서 종류와 무관한 **결재 엔진 하나**를 만들어
구매품의서·지급결의서(→ 정산내역서·견적요청서)에 붙이고, MES 도 같은 엔진으로 옮길 수 있게 짠다.

## 1. 지금 상태 (2026-09-28 조사)

### 회계
| 있는 것 | 실제 |
|---|---|
| 결재선 프리셋(`approval_presets`) | `steps=[{label, position}]` — **사람(계정)이 없다.** 직위 이름 문자열뿐 |
| 문서의 `approval` JSON | 프리셋을 문서마다 복사한 스냅샷 `[{label, position, name:''}]` — name 은 한 번도 안 채워짐 |
| 인쇄 결재란 | 둘째 줄이 **빈 칸** — 손으로 서명 |
| 상태 | 작성 → 승인 → 완료(`lib/docExec.js`). '반려' 없음 |
| 승인 권한 | 그 문서 자원의 `edit` 권한이면 **누구나**, 자기 문서도 승인 가능 |
| 사실상 후결 | `POST /resolutions/from-txn`(이미 나간 돈에 결의서), 이미 나간 지출로 만든 품의(승인 즉시 완료) |
| 로그인 계정 ↔ 직원 | **연결 없음** — 계정의 직위·부서를 모른다 |
| 알림(종) | 서버 저장 없음, 화면이 그때그때 계산. 사람별 수신함 없음 |
| 정산내역서·견적요청서 | 승인 흐름 자체가 없음(견적요청서는 결재란도 없음) |
| 앱 안내(FAQ, App.jsx:1160) | "결재선 순서대로 승인·현재 결재자 확인" — **실제와 다르다**(고칠 것) |

### MES (`dongjin-mes`, 태인 MES 를 단순화해 옮긴 것)
- 표 2개: `COERP_EIS_APPROVAL`(헤더: 1요청·2승인·3반려) + `COERP_EIS_APPRLINE`(차수 0=기안자, 1~3 결재자, 미결/완결/반려, `appr_read`=현재 차례)
- 상신 → 차수 순서대로 승인 → 마지막이면 원본(발주) '발주완료'. 반려는 **즉시 종료**, 원본은 '발주등록'으로 돌아가고 결재 번호 연결이 끊긴다. 재상신 = 새 결재번호
- 결재자는 기안자가 매번 1~3명 직접 고른다(템플릿 없음). 후보는 공통코드 `APPR_USER`
- '전결' = 이름이 '전결'로 시작하는 차수를 **건너뛴다**(일반적 의미의 전결이 아님). '후결'은 칸만 있고 동작 없음
- 결재함: 미결(내 차례)·완결·반려. 알림 없음. 인쇄 결재란은 이름·상태 글자(서명 이미지 없음, 업로드 기능은 있음)
- ⚠ 결함: 승인·반려에 잠금 없음(이중 승인 가능) / 전원 전결이면 멈춤 / 원본 상태 확인 없이 덮어씀 / 결재선 조회 권한 검사 없음 — **새 엔진은 이걸 되풀이하지 않는다**

## 2. 원칙

| # | 원칙 |
|---|---|
| A1 | **엔진은 문서를 모른다.** 문서 종류는 등록표(레지스트리)로 붙는다 — 승인 끝·반려·회수 때 무엇을 할지는 그 문서가 정한다. MES 발주도 나중에 같은 방식으로 붙는다 |
| A2 | **결재자는 사람(로그인 계정)이다.** 직위는 표시용 스냅샷. 차례가 온 그 사람만 누를 수 있다 |
| A3 | **이력은 지우지 않는다.** 반려·재상신·회수 모두 기록이 남는다(MES 처럼 연결을 끊지 않는다) |
| A4 | 돈을 움직이는 규칙(마감·이중계상 가드·docExec)은 **그대로** — 결재는 '누가 허락했나'만 바꾼다 |
| A5 | 결재 동작은 **한 트랜잭션 + 행 잠금**(FOR UPDATE). 같은 차례를 두 번 처리하지 못한다 |
| A6 | 결재함·알림은 **질의로 계산**한다(따로 쌓는 수신함 표는 나중). '내 차례'가 곧 결재할 문서다 |

## 3. 데이터 (테넌트 DB)

```sql
-- 결재 한 건 = 문서 한 번의 상신(회차). 반려 후 다시 올리면 새 행(round+1) — 이력이 남는다
CREATE TABLE approvals (
  id            VARCHAR(36) PRIMARY KEY,
  doc_type      VARCHAR(30)  NOT NULL,     -- 'purchase_req' | 'resolution' | 'settlement' | 'quote_req' | (후일) 'mes_pur_order'
  doc_id        VARCHAR(36)  NOT NULL,
  round         INT          NOT NULL DEFAULT 1,
  title         VARCHAR(200),              -- 결재함 표시용 스냅샷(문서번호·거래처·금액)
  amount        BIGINT,                    -- 전결 규칙 판정용 스냅샷
  mode          VARCHAR(10)  NOT NULL DEFAULT 'normal',   -- 'normal' | 'post'(후결)
  status        VARCHAR(10)  NOT NULL,     -- '진행' | '승인' | '반려' | '회수'
  drafter_id    VARCHAR(36)  NOT NULL,     -- 플랫폼 users.id
  drafter_name  VARCHAR(100),
  drafter_pos   VARCHAR(50),
  submitted_at  DATETIME     NOT NULL,
  finished_at   DATETIME,
  KEY ix_doc (doc_type, doc_id),
  KEY ix_status (status)
);

-- 결재선 한 줄 = 한 사람의 한 차례
CREATE TABLE approval_steps (
  id            VARCHAR(36) PRIMARY KEY,
  approval_id   VARCHAR(36)  NOT NULL,
  seq           INT          NOT NULL,     -- 1..n (순서)
  kind          VARCHAR(10)  NOT NULL DEFAULT '결재',     -- '결재' | '참조'(참조는 차례 없이 보기만)
  approver_id   VARCHAR(36)  NOT NULL,
  approver_name VARCHAR(100),
  approver_pos  VARCHAR(50),
  label         VARCHAR(30),               -- 결재란 머리글(담당·팀장·대표…) — 인쇄 결재란과 같은 뜻
  status        VARCHAR(10)  NOT NULL,     -- '대기' | '차례' | '승인' | '반려' | '전결' | '생략'
  acted_at      DATETIME,
  comment       VARCHAR(500),              -- 첨언 · 반려 사유(반려는 필수)
  UNIQUE KEY uq_step (approval_id, seq),
  KEY ix_turn (approver_id, status),       -- '내 차례' 결재함
  FOREIGN KEY (approval_id) REFERENCES approvals(id) ON DELETE CASCADE
);
```

- **결재선 프리셋**(`approval_presets.steps`)에 사람을 싣는다: `[{label, position, user_id?}]`. user_id 가 비면 상신 때 기안자가 고른다.
- 문서 쪽 `approval` JSON(인쇄 결재란 스냅샷)은 **은퇴**한다 — 결재란은 `approval_steps` 에서 그린다(옛 문서는 JSON 그대로 인쇄).
- **계정 ↔ 직위·부서**: 결재란·결재함에 직위가 필요하다 → 열린 결정 Q1.

## 4. 흐름

### 4-1. 기본(정상 결재)
```
작성 ──상신──▶ 결재중 ──(1차 승인)──▶ … ──(마지막 승인)──▶ 승인 ──지출 처리──▶ 완료
   ▲              │                                  │
   │            회수(첫 승인 전, 기안자)             반려(사유 필수, 어느 차례든)
   └──────────────┴──────────────────────────────────┘   → 문서는 '작성'으로, 고쳐서 재상신(round+1)
```
- **상신**: 기안자가 결재선을 확인(프리셋에서 채워짐, 고칠 수 있음) → 첫 '결재' 차례가 '차례'가 된다.
- **승인**: 차례인 사람만. 다음 '결재' 차례로 넘어간다. 마지막이면 결재 '승인' → 문서 등록표의 `onApproved`(= 지금의 approveDoc: 작성→승인, 돈이 이미 나간 문서는 바로 완료).
- **반려**: 차례인 사람만, 사유 필수. 결재 '반려'로 끝나고 문서는 '작성'. 기안자가 고쳐 **재상신**(새 회차, 앞 회차 기록은 남는다).
- **회수**: 기안자가, 아직 아무도 승인하지 않았을 때만. 결재 '회수', 문서 '작성'.
- **결재중 잠금**: 결재중인 문서는 고칠 수 없다(회수 먼저). 승인된 문서를 고치면 지금처럼 '작성'으로 돌아가고 결재도 다시 받아야 한다(A4 기존 규칙 유지).

### 4-2. 전결 — 윗선을 대신해 최종 결재
- 차례인 사람이 **'전결'**을 누르면 그 뒤 차례들은 '생략'이 되고 결재가 끝난다(승인과 같은 결과).
- 누가 전결할 수 있나 → **Q2 결정: 결재자 판단** — 차례인 결재자는 언제든 [전결]을 누를 수 있다(규칙표 없음). 누가 전결했는지는 이력·결재란에 남는다.
- 결재란에는 생략된 칸에 '전결' 표시(관행대로 사선·'전결' 글자). MES 의 '건너뛰기 전결'과 뜻이 다르다 — 통일할 때 MES 쪽을 이 뜻으로 바꾼다.

### 4-3. 후결 — 먼저 처리, 결재는 나중
- 긴급 건: 기안자가 **'후결로 상신'** → 결재는 '진행'인데 문서는 곧바로 **처리(지출) 가능**.
- 결재가 끝나면 그대로. **반려되면** 이미 돈이 나갔으므로 자동으로 되돌리지 않는다 — 문서에 '후결 반려' 표시가 붙고 기안자·관리자 결재함 맨 위에 뜬다(처리 취소는 사람이 판단).
- 지금 이미 있는 '사실상 후결' 경로(이미 나간 돈에 결의서 붙이기, 이미 나간 지출로 만든 품의)는 **자동으로 후결 모드**가 된다.
- 누가 쓸 수 있나 → **Q3 결정: 기안자가 '긴급(후결)' 체크 + 사유 필수.** 1단계부터 넣는다.

## 5. 문서 등록표 (엔진 ↔ 문서)

```js
// lib/approvalDocs.js — 문서 종류마다 한 줄. 엔진(lib/approval.js)은 이것만 안다
purchase_req: {
  table: 'purchase_reqs', label: '구매품의서',
  snapshot: (doc) => ({ title: `${doc.doc_no} · ${doc.vendor_name}`, amount: doc.order_amount }),
  canSubmit: (doc) => doc.status === '작성',
  onApproved:  (conn, doc) => approveDoc(conn, 'purchase_reqs', doc.id),   // 지금 규칙 그대로
  onRejected:  (conn, doc) => backToDraft(conn, 'purchase_reqs', doc.id),
  onRecalled:  (conn, doc) => backToDraft(conn, 'purchase_reqs', doc.id),
},
resolution: { … 같은 모양 … },
```
- 문서 상태 칸은 지금 값(작성·승인·완료)에 **'결재중'** 하나만 더한다. '반려'는 결재 쪽 상태이고 문서는 '작성'으로 돌아간다(목록에는 '반려됨' 표시).
- `docExec` 의 approve/unapprove 엔드포인트는 결재 엔진을 거치게 바꾼다(직접 '승인' 버튼은 없앤다 — 관리자 예외는 Q4).
- MES 발주는 나중에 `mes_pur_order` 한 줄로 붙는다(onApproved = MES 발주 '발주완료'). 그때 MES 결재함은 이 엔진을 부른다.

## 6. 화면

| 자리 | 내용 |
|---|---|
| **결재함**(새 메뉴, 문서업무 맨 위) | 탭: **결재할 문서**(내 차례) · 올린 문서(진행중·반려) · 완료 · 참조. 행을 누르면 문서 미리보기 + 결재선 + [승인][반려][전결] |
| 문서 화면(품의·결의) | '승인' 버튼 → **[결재 올리기]**. 결재중이면 결재선 진행 표시(누가 승인했고 지금 누구 차례인지), 기안자에겐 [회수] |
| 상신 창 | 결재선(프리셋에서 채움·사람 고르기·순서 바꾸기·참조 추가), 후결 체크(권한 있는 사람), 첨언 |
| 종(알림) | '결재할 문서 n건', '반려된 내 문서 n건'(질의 계산). 사이드바 결재함에 숫자 배지 |
| 인쇄 결재란 | 칸마다 **이름·승인일**(서명 이미지는 3단계). 전결 칸 사선, 후결 표시 |
| 환경설정 › 결재선 | 단계마다 **사람**을 지정할 수 있게(비우면 상신 때 고름). 문서 종류별 기본 결재선 |

## 7. 권한

- 결재 **동작**(승인·반려·전결)은 권한 표가 아니라 **"지금 차례인 사람인가"** 로 판정한다(서버, 행 잠금 안에서).
- 상신·회수는 그 문서의 `create/edit` 권한 + 기안자 본인.
- 결재함 조회는 로그인만 되면(ANY_AUTHENTICATED) — 목록은 **나와 관련된 것만** 서버가 거른다.
- 결재자 후보 목록 API 가 새로 필요하다(지금 사용자 목록은 마스터 전용) — 이름·직위만 준다.
- 감사: 상신·승인·반려·전결·회수·후결 모두 `approval_steps`(문서별 이력) + `audit_logs`(전역).

## 8. MES 통일 대응표 (나중)

| MES | 이 엔진 |
|---|---|
| `EIS_APPROVAL.appr_stat` 1/2/3 | `approvals.status` 진행/승인/반려 |
| `EIS_APPRLINE.appr_stat` 미결/완결/반려 + `appr_read` | `approval_steps.status` 대기·차례/승인/반려 |
| '전결' 이름 접두어(건너뛰기) | `status='생략'`(전결자 뒤 차례) — 뜻을 이쪽으로 맞춘다 |
| `PUR_ORDER.afte_conf` 미결/후결/완결 | `approvals.mode='post'` + status |
| `appr_gubu` + `docu_numb` | `doc_type` + `doc_id` |
| 결재자 `COERP_SYS_USER_INFO` | 회계 플랫폼 users — **계정 체계가 다르다.** 통일 때 계정 연결 방식을 따로 정한다 |

## 9. 단계

| 단계 | 내용 |
|---|---|
| **1** | 엔진(표 2개·상신·승인·반려·회수·잠금) + 구매품의서·지급결의서 연결 + 결재함 + 종 알림 + 결재란에 이름·날짜 + 결재선 프리셋에 사람 |
| **2** | 전결 규칙 + 후결(기존 '사실상 후결' 경로 흡수) |
| **3** | 정산내역서·견적요청서 연결(Q5), 서명 이미지, 계정↔직원 연결 |
| **4** | MES 통일(동진) — MES 발주를 등록표에 붙이고 MES 결재함이 이 엔진을 쓴다 |

## 10. 열린 결정

| # | 질문 | 제안 |
|---|---|---|
| Q1 | 결재자는 **로그인 계정**인가(대표·이사도 계정이 있어야 결재 가능) | 계정. 계정에 직위·부서 칸을 붙인다(직원 대장 연결은 3단계) |
| Q2 | **전결**은 누가·언제 | 문서 종류 × 금액 규칙(예: 100만원 이하는 팀장 전결). 규칙에 맞을 때만 전결 버튼이 보인다 |
| Q3 | **후결**은 누가 | 기안자가 '긴급'으로 체크, 사유 필수. 관리자가 켠 문서 종류에서만 |
| Q4 | 결재 없이 **관리자가 바로 승인**하는 길을 남기나(작은 회사·혼자 쓰는 회사) | 남긴다 — 회사 설정 '전자결재 쓰기'가 꺼져 있으면 지금처럼 승인 버튼. 켜면 결재만 |
| Q5 | 정산내역서·견적요청서도 결재 대상인가 | 정산내역서 예, 견적요청서 아니오(대외 발송 문서) |
| Q6 | 알림은 앱 안(종·결재함)만인가, 이메일·카톡도인가 | 1단계는 앱 안. 이메일은 나중 |
