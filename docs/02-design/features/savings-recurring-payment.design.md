## 0. 요약 (TL;DR)

예금·적금·보증금 화면(`finance_savings`)은 지금 **적금만, 매월, 원금만** 처리할 수 있다.
실무에서 나가는 돈은 그렇게 생기지 않았다 — 분기·반기·연 납입이 있고, 원금 옆에
수수료·보험료 같은 부대비용이 함께 빠진다.

이 문서는 세 가지를 더한다.

1. **납입 주기** — 월/분기/반기/연
2. **회차별 부대비용** — 수수료 등. 원금과 **다른 거래로** 기록한다
3. **예금·퇴직연금도 회차 납입** — 지금은 적금만 허용

**가장 중요한 원칙**: 원금은 자산 이동(손익 아님), 부대비용은 비용(손익)이다.
한 거래로 뭉치면 비용이 실제보다 적게, 회사 재산이 실제보다 많게 잡힌다.

## 1. 현행 진단

### 1.1 되는 것과 안 되는 것

| 항목 | 현재 | 근거 |
|---|---|---|
| 회차 납입 | **적금만** | `routes/savings.js` `/pay` — `kind !== 'installment'` 면 400 |
| 납입 주기 | **월 고정** | `lib/savings.js` `paymentSchedule()` — `term_months` 만큼 매월 1회차 |
| 부대비용 | **자리 없음** | `applyPayment()` 가 거래를 1건(회차 금액)만 만든다 |
| 예금·퇴직연금 적립 반영 | 금액 수정뿐 | 거래가 안 생겨 통장에서 빠진 돈과 이어지지 않는다 |

### 1.2 왜 문제인가

- **주기**: 분기 납입을 월 납입으로 우겨넣으면 회차 수와 예정일이 전부 틀린다.
  자금 예측이 "며칠에 얼마 나가나"를 답할 수 없게 된다 — 이 화면의 존재 이유가 없어진다.
- **부대비용**: 수수료를 원금에 얹으면 금융상품 계정(1201/1505)으로 들어가
  **비용이 사라지고 자산이 부푼다.** 만기 수령에서 원금과 이자를 두 거래로 나눈 것과
  정확히 같은 이유로, 여기서도 나눠야 한다.
- **퇴직연금**: 매월·분기 납입이 실무의 보통 모습인데 회차 기능이 막혀 있어,
  적립금이 늘 때마다 금액을 손으로 고쳐야 한다. 그러면 **거래 기록이 남지 않는다.**

## 2. 데이터 모델

### 2.1 `savings` — 주기 컬럼 추가

```sql
pay_cycle  VARCHAR(10) NOT NULL DEFAULT 'monthly'   -- monthly|quarterly|semiannual|annual
```

- 기존 행은 전부 `monthly` 로 시작한다 — **지금 숫자가 하나도 바뀌지 않는다.**
- `term_months` 의 뜻은 그대로 **총 기간(개월)**이다. 회차 수가 아니다.
  회차 수 = `term_months / 주기개월` (내림). 이렇게 두면 "3년 만기"가 주기와 무관하게 같은 말이 된다.

| pay_cycle | 주기(개월) | 36개월 상품의 회차 수 |
|---|---|---|
| monthly | 1 | 36 |
| quarterly | 3 | 12 |
| semiannual | 6 | 6 |
| annual | 12 | 3 |

⚠ `term_months` 를 회차 수로 바꾸는 안은 **버린다.** 기존 데이터의 뜻이 조용히 달라져
이미 등록된 적금의 만기일이 전부 틀어진다(12개월 적금이 12년짜리가 된다).

### 2.2 `savings_payments` — 부대비용 칸 추가

```sql
fee            BIGINT DEFAULT 0,      -- 그 회차에 함께 나간 수수료 등(원금과 별도)
fee_acct_code  VARCHAR(10),           -- 비용 계정과목. 비면 5219(지급수수료) 기본
txn_fee_id     VARCHAR(36)            -- 부대비용 거래 id (원금 거래는 기존 txn_id)
```

- `fee = 0` 이 기본이라 기존 회차는 그대로다.
- **`amount` 에 수수료를 더하지 않는다.** `amount` 는 끝까지 원금이다 —
  `paidPrincipal()` 이 이 값을 합산해 '묶인 자금'을 내므로, 수수료를 섞으면
  쓰지도 못하는 수수료가 회사 재산으로 잡힌다.

### 2.3 계정과목

| 항목 | 계정 | 손익 |
|---|---|---|
| 원금 납입 | 1201 단기금융상품 / 1501 장기금융상품 / 1505 퇴직연금운용자산 | **아님**(자산 이동) |
| 부대비용 | 5219 지급수수료(기본) · 5212 보험료 등 선택 가능 | **비용** |
| 만기 이자 | 4201 이자수익 | 수익 |

> 확인함 — `data/account-subjects.json` 에 **5219 지급수수료**, **5212 보험료** 모두 있다.
> 새 계정과목을 더할 필요는 없다. (5203 은 지급수수료가 아니라 **복리후생비**다 — 헷갈리기 쉽다.)

## 3. 로직

### 3.1 회차 예정일

```js
const CYCLE_MONTHS = { monthly: 1, quarterly: 3, semiannual: 6, annual: 12 }

function paymentSchedule(s) {
  const step = CYCLE_MONTHS[s.pay_cycle] || 1
  const n = Math.floor(term_months / step)      // 회차 수
  // i 회차 예정일 = dueDateOf(start_date, pay_day, (i - 1) * step)
}
```

- 1회차는 가입일 당일이다(현행 규칙 유지 — 대출과 방향이 반대라 한 칸 당긴다).
- 말일 처리는 `dueDateOf` 가 이미 한다(1/31 + 3개월 = 4/30).

### 3.2 적금 이자 — 주기가 들어가면 공식이 바뀐다

현행 공식은 **월 납입 전제**다.

```
총이자 = 월납입 × (연이율/12) × n(n+1)/2
```

주기가 `step` 개월이면 회차 사이 간격이 `step` 개월이므로:

```
총이자 = 회차납입 × (연이율/12) × step × n(n+1)/2
```

⚠ 이 자리를 안 고치면 **분기 적금의 이자가 1/3로 나온다.** 회차 수만 줄고 예치 기간이
안 늘어나기 때문이다. 테스트로 잠근다(현행 월 납입 케이스의 값이 안 변하는지도 함께).

### 3.3 납입 처리 — 거래 2건

`applyPayment()` 를 고친다.

```
원금 거래     kind=expense  category='적금 납입'   account_code = s.acct_code
부대비용 거래  kind=expense  category='지급수수료'  account_code = fee_acct_code   ← fee > 0 일 때만
```

- 한 트랜잭션 안에서 만든다. 하나만 남으면 통장 잔액과 어긋난다.
- 납입 취소는 **두 거래를 함께** 지운다(현행 취소 로직에 `txn_fee_id` 를 더한다).

### 3.4 회차 납입을 여는 종류

| kind | 회차 납입 | 이유 |
|---|---|---|
| installment 적금 | ✅ 현행 | |
| **pension 퇴직연금** | ✅ **연다** | 매월·분기 납입이 실무의 보통 |
| deposit 예금 | ❌ 그대로 | 목돈을 한 번에 넣는 상품이다. 회차가 생기면 예금이 아니다 |
| guarantee 보증금 | ❌ 그대로 | 한 번 내고 끝난다 |

퇴직연금은 **만기가 없으므로** 회차 수를 기간에서 뽑을 수 없다. 그래서:

- `term_months = 0` 을 유지하고, 예정 회차를 **미리 깔지 않는다**
- 대신 "이번 회차 납입" 버튼으로 **그때그때 한 건씩** 기록한다
  (`savings_payments` 에 seq 를 이어붙이고 `principal` 을 그만큼 올린다)
- 자금 예측에는 정기지출과 같은 방식으로 다음 예정일만 노출한다

> 이 부분은 적금과 구조가 달라, 구현 시 `savings_payments` 를 공유하되
> "예정 회차를 미리 까는가"만 갈린다. 한 테이블을 쓰는 편이 묶인 자금 집계가 한 곳에 남는다.

## 4. 화면

### 4.1 등록 폼

- **납입 주기** 칩 추가 — 월 / 분기 / 반기 / 연. 기본 '월'
- 기간 라벨을 "기간 (개월)" 그대로 두되, 아래에 계산된 회차 수를 보여준다
  → "36개월 · 분기 납입 → 12회차"
- 퇴직연금은 기간 칸 대신 **납입 주기만** 받는다(만기가 없다)

### 4.2 납입 드로어

- 원금 칸 아래 **수수료 칸** 추가(기본 0, 비워도 됨)
- 수수료를 넣으면 "원금 ○○원은 자산으로, 수수료 ○○원은 비용으로 각각 기록됩니다" 안내
  — 이 화면이 계속 드러내야 하는 것이 "납입은 비용이 아니다"라서, 예외를 명시해야 한다

### 4.3 상세 펼침

- 회차 표에 수수료 열 추가. 합계 행에 **원금 합계 / 수수료 합계를 나눠서** 적는다

## 5. 마이그레이션

전부 **값을 넓히기만** 하는 변경이라 기존 데이터가 안 바뀐다.

```js
await ensureColumn('savings',          'pay_cycle',     "pay_cycle VARCHAR(10) NOT NULL DEFAULT 'monthly'")
await ensureColumn('savings_payments', 'fee',           "fee BIGINT DEFAULT 0")
await ensureColumn('savings_payments', 'fee_acct_code', "fee_acct_code VARCHAR(10)")
await ensureColumn('savings_payments', 'txn_fee_id',    "txn_fee_id VARCHAR(36)")
```

기존 행: `pay_cycle='monthly'`, `fee=0` → **현행과 완전히 같은 동작.**

## 7. 하지 않는 것

- **퇴직급여충당부채(2304) 상계** — 퇴직연금 지급 시 자산·부채를 함께 줄이는 처리.
  지금 충당부채 관리 자체가 없어 범위를 넘는다. 그래서 퇴직연금은 만기 수령을 막아 두었다
  (`routes/savings.js` `/mature`).
- **DC형 퇴직연금** — 납입 즉시 회사 돈이 아니게 되므로 이 화면이 아니다. 정기지출에서
  퇴직급여(5202) 비용으로 처리한다.
- **복리 상품** — 실무 상품 대부분이 단리다. 필요해지면 그때 `interest_method` 를 더한다.
