> 정기는 그냥 없애고 반복거래처럼, 진짜 회차 추적보단 복사해서 입력을 도와주는 형태로.

알찬회계 반복거래(gno 18): 원본 전표를 등록 → 목록(일자순) 체크 → 한 번에 생성. 일자만 저장, 회차 추적·자동 생성·놓친 달 없음.

확정(2026-09-15 질문 답):
1. **출금은 반복거래마다 고른다** — 바로 출금 거래 / 청구서(지급 대기). 입금(매출)은 늘 청구서(미수금).
2. **정기형 계약은 등록·금액만 연동** — 계약을 만들면 반복거래가 생기고, 금액·일자·주기를 고치면 따라간다. 갱신·종료·방식변경 연동은 없앤다. 계약이 진행중이고 기간 안일 때만 그 달 목록에 뜬다(계산).
3. **지난달은 달을 골라 보기만** — 경고·배지 없음.
4. **자금 예측에 넣는다** — 아직 안 만든 반복거래를 다음 날짜의 예상 금액으로.

## 결정

### 1. 표 — `repeat_templates` 하나

| 칸 | 뜻 |
|---|---|
| `direction` in/out | 입금·출금 |
| `creates` invoice/txn | 만들 것. 입금은 늘 invoice |
| `vendor_id`, `contract_id` | 거래처, 계약(선택) |
| `item` | 내용. `{월}` 은 만들 때 그 달 숫자로 바뀐다 |
| `category` | 비목(출금) |
| `amount`, `vat_mode` | 금액과 부가세 — exclusive(별도) / inclusive(포함) / none(면세) / zero(영세) |
| `period`, `anchor_month` | 매월·격월·분기·매년 + 기준 달(매월 외) |
| `day_of_month` | 1–31(말일 clamp). 0 = 만들 때 날짜를 고른다 |
| `account_id` | 계좌(바로 출금은 필수) |
| `pay_term`, `pay_day` | 청구서 결제기한(기존 규칙 그대로) |
| `active` | 사용 |

**없앤 것:** 시작·종료일(계약 없는 반복거래는 켜고 끄기, 계약 연결은 계약 기간이 정한다), `last_generated`, 건너뛰기, 소급 묶음, 변동형 플래그(만들 때 금액을 늘 고칠 수 있다), 증빙 요구 플래그.

`invoices.template_id`, `transactions.template_id` 로 "어느 반복거래에서 만들었나"만 남긴다(FK 없음 — 템플릿을 지워도 장부는 그대로).

### 2. "이번 달 만든 것 있음" — 저장하지 않고 계산
그 달에 해당하는 반복거래(주기·기준 달·계약 기간)마다, **같은 template_id 로 그 달에 날짜가 든 청구서·거래**가 있으면 '만듦'(번호 링크). 없으면 체크할 수 있다.
만든 것을 지우면 자연히 다시 '안 만듦'이 된다 — 되돌리는 코드가 필요 없다.

### 3. 화면 — 입출금 › 반복거래 (한 화면)
- 위: `[◀ 2026년 9월 ▶]` `[전체·입금·출금]` `[이번 달 | 전체 목록]` `[+ 반복거래]`
- 이번 달: 일자순 표 — ☐ · 날짜 · 입금/출금 · 거래처 · 내용 · 금액 · 만들 것 · (만듦이면 번호)
- `[선택한 N건 만들기]` → 확인 서랍: 줄마다 **날짜·금액 고치기**, 바로 출금이면 계좌.
  - 이미 비슷한 것이 있으면(같은 거래처·금액, 그 달, template 없음 — 통장·홈택스로 먼저 들어온 것) 그 줄에 표시하고 기본은 **그것에 연결**(template_id 만 붙인다). [새로 만들기]로 바꿀 수 있다.
- 전체 목록: 모든 반복거래(꺼진 것 포함), 줄을 누르면 수정.
- 반복거래 서랍: 입금/출금 → (출금) 바로 출금/청구서 → 거래처·계약 → 내용·비목 → 금액·부가세 → 주기·일자 → 계좌·결제기한.

### 4. 만들기 규칙 (서버 lib/repeat.js 한 곳)
- 입금 → 매출 청구서(`createInvoice`, origin `repeat`), 발행일 = 날짜, 결제기한 = pay_term.
- 출금·청구서 → 매입 청구서(지급 대기), 비목 계정 포함.
- 출금·바로 → 지출 거래(지급완료). **오늘까지만**, 계좌 필수, 마감 검사, 부가세 칸. 거래 만드는 규칙은 결의서 처리(docExec)와 **같은 lib**로 떼어낸다(`lib/directTxn.js`) — 세 벌 금지.
- 공통: 마감된 달 거절, 금액 0 거절, 같은 template·같은 달에 이미 있으면 거절(두 번 누름·두 탭).
- 이미 있는 돈에 붙이기: 붙일 청구서·거래도 **그 달 날짜**여야 한다(다른 달 건에 붙이면 이 달이 계속 '안 만듦'). 후보 찾기도 그 달로 자른다.

### 5. 계약 연동 (등록·금액만)
- 정기형 계약 등록 → 반복거래 생성(매출 계약 → 입금·청구서, 매입 계약 → 출금·청구서).
- 계약 금액(주기당)·청구일·주기·과세유형·거래처를 고치면 **계약과 같은 방향 반복거래 하나**만 같은 값으로.
  같은 방향이 둘 이상이면 건드리지 않는다. 다른 방향(매출 계약에 원가로 붙인 출금)은 연동 대상이 아니다
  — 계약 저장 한 번에 원가 반복거래 금액이 계약 금액으로 덮이던 결함(구현 검토에서 발견).
- 정기형 → 다른 방식으로 바꾸면 같은 방향 반복거래를 **끈다**(지우지 않는다). 계산으로 숨기면 왜 안 뜨는지 안 보이고,
  남겨 두면 청구 일정과 반복거래로 같은 돈을 두 번 청구한다.
- **없앤다:** 갱신 시 종료일 연장, 완료·미갱신 시 종료일 채우기, 열린 규칙 조회, 계약 상세의 정기 규칙 켜기/동기화 버튼.
- 목록 노출 조건(계산): 계약이 `진행중` 이고 그 날짜가 계약 시작일~종료일(없으면 무기한) 안.
  청구 방식은 **보지 않는다** — 옛 정기지출은 총액형 발주에도 붙어 돌았고, 방식으로 거르면 옮긴 반복거래가 말없이 사라진다.
  전체 목록은 켜져 있는데 계약 때문에 안 뜨는 것에 이유를 적는다(`hidden_reason`).
- 계약 상세 이행률: 같은 방향·켜진 반복거래만. 기간 안에 도래한 달 × 금액(도래액) vs 청구서 합계 + 바로 출금 거래 합계.

### 7. 옮기기 (runOnce)
- 두 표의 행을 **같은 id** 로 `repeat_templates` 에 넣는다 → `invoices/transactions.template_id = recurring_id` 한 줄로 끝.
- 기준일 = 시작일, 없으면 등록일. 기준 달 = 기준일의 달, 청구일이 비었거나 0이면 기준일의 일자(옛 recurrence.js 앵커 규칙).
- 매출: amount=공급가, vat_mode=계약 과세유형 우선(기존 effRecurVatMode), period·day, creates=invoice.
- 매입: amount=합계, vat_mode=inclusive(면세·영세면 그대로), creates = 당일 출금(`immediate`)이면 **txn**, 아니면 invoice. 종료일이 지난 것은 active=0.
- 옛 표는 **지우지 않는다**(되돌릴 길). 코드만 안 쓴다. 한두 달 뒤 정리.

## 검증 기록 (2026-09-18, 로컬 `repeat` 테넌트)

fowin 모양의 옛 정기 규칙 27건(매출 20·매입 7)을 심어 `npm run setup:db` 로 이관을 돌리고,
시나리오 1~9 를 화면과 API 로 확인했다. 전건 통과.

- **이관** — 27 → 27, 한 줄씩 대조(금액·과세유형·주기·일자·기준달·사용·계약)까지 일치.
  청구서 20/20 · 거래 7/7 에 `template_id` 가 붙고, 옛 표는 그대로 남았다.
  옛 `last_generated` 가 9월로 적힌 13건과 새 '그 달 만듦' 판정 13건이 같았다.
  청구일이 빈 규칙은 시작일의 일자(25일)로, 31일 규칙은 달마다 말일로 clamp(9월 30·2월 28).
- **주기** — 3월에만 연 1회, 3·6·9·12월에 분기, 홀수달에 격월. 꺼진 것·계약 완료 건은 안 뜬다.
- **만들기** — 확인 서랍에서 날짜·금액을 고친 값 그대로 만들어지고, 두 번째는 409.
  마감된 달 거절, 다른 달 날짜 거절, 바로 출금의 미래 날짜 거절, 한 줄이라도 막히면 아무것도 안 만든다.
- **붙이기** — 먼저 들어온 청구서가 있으면 409 로 물어보고, 연결하면 새로 만들지 않고 `template_id` 만 붙는다(그 달 1건).
- **되돌리기** — 만든 청구서를 지우면 그 달이 다시 '안 만듦'.
- **계약** — 등록 시 생성, 금액·주기·일자·과세유형은 따라가고, 원가로 붙인 반대 방향 반복거래는 안 건드린다.
  정기형을 다른 방식으로 바꾸면 끈다(안 지운다). 계약이 완료면 달별 목록에서 빠지고 전체 목록이 이유를 말한다.
- **기대던 곳** — 대시보드 월 환산, 자금 예측(그 달 만든 것은 빼고), 입력 힌트, 거래처 끄기 안내, 계좌 삭제 차단.

### 검증에서 고친 것 3건

1. **달별 목록이 날짜순으로 안 읽혔다.** 화면은 만든 줄에 **실제로 만든 날짜**를 보여주는데
   서버 정렬은 틀의 예정일만 봤다 — 10일짜리를 25일에 만들면 10일 자리에 25일이 앉는다.
   정렬 키를 화면이 보여주는 날짜(`made?.date || date`)로 맞췄다(`lib/repeat.js`).
2. **확인 서랍 합계가 목록 합계와 달랐다.** 서랍은 입력칸 값을 그대로 더해 부가세 별도면 공급가만
   셌다(같은 2건이 목록 4,840,000 · 서랍 4,600,000). 서랍도 합계(부가세 포함)로 센다(`Repeat.jsx`, `lib/vatRate.js`).
3. **권한 경계가 무너져 있었다.** 입금·출금이 한 라우트로 합쳐지며 권한 게이트가 자원군 OR 이 됐고,
   출금 권한만 가진 역할이 입금 반복거래 18건을 읽고 **매출 청구서까지 만들었다**
   (정작 `/api/invoices` 는 403 인데 여기로 우회됐다 — 실측). 줄마다 방향의 자원을 다시 따진다
   (`routes/repeat-templates.js`). 역할 미배정 계정은 `perm.js` 와 같게 통과시킨다.

### 코드 품질 검토에서 고친 것 9건 (2026-09-18)

지적을 그대로 믿지 않고 먼저 재현시켰다 — 1·2·3·4는 실제로 재현됐다.

1. **이중 계상 가드가 화면에서 늘 꺼져 있었다.** 확인 서랍은 후보가 없던 줄에도 `force_new` 를 붙여
   보내, 서랍을 연 뒤 통장·홈택스로 들어온 돈을 서버가 다시 볼 기회를 없앴다(같은 돈 두 줄. 재현).
   서랍의 lookalike 복구 분기도 그래서 죽은 코드였다. **사람이 후보를 보고 '새로 만들기'를 고른 줄에만** 붙인다.
2. **반복거래만 붙은 거래처가 그냥 지워졌다.** `repeat_templates` 는 FK 가 없고(설계), 이관이 옛 표의 FK 도 걷어
   막을 것이 없었다. 지운 뒤 그 반복거래는 거래처 '—' 로 목록에 떠 있다가 만들 때 500 이 났다(재현).
   삭제 전에 반복거래 건수를 세어 막는다.
3. **정기형 → 단건 → 정기형 으로 되돌리면 반복거래가 꺼진 채였다.** sync 가 금액·주기는 맞추면서 `active` 는
   안 되돌렸다. 계약은 정기형인데 달별 목록에 영영 안 뜬다(재현). 되돌릴 때 함께 켠다. 틀린 주석도 고쳤다.
4. **바로 출금의 예정일이 아직 안 왔으면 묶음 전체가 죽었다.** 서랍 기본 날짜가 예정일(28일)인데 입력칸 max 는
   오늘이라 손댈 수도 없고, 만들기는 전부 아니면 전무라 같이 고른 줄까지 안 만들어졌다(재현).
   이번 달을 볼 때는 오늘로 당겨 채우고, 보내기 전에 화면에서 막는다.
5. 계약 상세가 달마다 쿼리를 두 번씩 돌렸다(2020년부터면 왕복 100회 넘음) — 한 번에 읽는다.
6. 계약의 거래처를 매출처↔매입처로 바꾸면 반대 방향 반복거래가 **하나 더** 생기고 옛 것이 켜진 채 남았다.
   옛 방향 것을 끈다(그 방향에 여러 벌이면 손대지 않는다 — 원가 반복거래를 끄면 안 된다).
7. 이관이 등록 폼의 제약을 건너뛰었다 — 계좌 없는 당일 출금을 '바로 출금'으로 옮기면 만들 때 400 이 난다.
   계좌가 없으면 청구서로 옮긴다.
8. 붙이기가 화면이 보낸 아무 id 나 받았다. 엉뚱한 건에 `template_id` 가 찍히면 그 달이 '만듦'으로 막혀
   정작 이 반복거래의 돈은 영영 안 만들어진다. **서버가 고른 후보 안에 있는지** 확인한다.
9. `seed.js` 가 아무도 안 읽는 옛 표에 넣고 있었다 — 반복거래 표로 옮겼다.

### 그 과정에서 드러난 것 — 계약이 만든 출금 반복거래엔 비목이 없다

`syncContractTemplates` 는 매입 계약으로 출금 반복거래를 만들면서 **비목을 안 채운다**(계약이 비목을 모른다).
등록 폼은 비목 없는 출금을 막는데 계약 경로가 그 문을 안 거쳤다 — 비목 없이 만든 지출은 전표의 비용 줄이 빈다.
지금은 목록이 **"비목을 골라주세요"** 로 말하고 그 줄을 고르지 못하게 한다(`needs_fix`).
옮겨 온 줄도 같은 자리에서 걸린다.

> 남은 판단: 매입 계약을 등록할 때 비목을 함께 받을지. 받으면 손이 하나 늘고, 안 받으면 반복거래에서 한 번 채워야 한다.
