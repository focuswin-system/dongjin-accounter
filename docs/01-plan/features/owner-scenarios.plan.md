# 대표님 사용 시나리오 — 현행 대비 분류

> 대표님이 정리해 주신 "이 프로그램을 쓰면서 생길 수 있는 상황"을 받아,
> 지금 코드로 **되는 것 / 되지만 불편한 것 / 새로 짜야 하는 것**으로 나눈 문서.
> 시나리오는 5~6개씩 나눠서 들어온다. **받는 대로 여기에 누적한다.**

## 분류 기준

| 구분 | 뜻 |
|---|---|
| **A** | 지금 그대로 된다. 워크플로가 거의 맞음 |
| **B** | 되긴 하는데 불편하거나 메뉴가 흩어져 있음 — 개선 가능 |
| **C** | 지금 구조로는 안 됨. 로직을 새로 짜야 함 |
| **D** | 시나리오가 드묾. 고려하면 오히려 프로그램이 망가짐 — 사용자가 적당히 입력 |

⚠ 분류는 **코드를 열어 확인한 것만** 적는다. 근거 파일·라인을 함께 남긴다.
  (실제로 1차에서 하나를 잘못 분류했다 — 아래 '정정' 참조)

## 정정 — 1차에서 잘못 분류한 것

**"미납 추적을 끄는 정액형" → C 가 아니라 A 다.**

정기입금 회차의 **'기입금 처리'** 버튼이 이미 그 일을 한다:
청구서를 `입금 완료` 로 발행하면서 실제 입금 거래와 `invoice_matches` 까지 한 번에 만든다
(`routes/recurring-invoices.js:238~` `paid` 분기). **미수금이 아예 안 생긴다.**

⚠ 추적 스위치를 따로 만들면 안 된다. "추적 안 함"으로 걸어 두면
   **진짜 안 들어온 달을 아무도 모른다.**

## 결정

### ① 외화·환율 — 만들지 않는다
통장에 찍힌 원화가 곧 실현된 금액이고 그게 장부의 진실이다.
외화 원장이 필요한 건 *결제 전까지 환율이 흔들리는 외화 미수금*을 따로 관리하고
환차손익을 신고해야 할 때인데, 그런 회사가 아니다.
넣으면 **모든 금액 칸에 통화가 붙고 집계·보고서가 두 겹이 된다.**
(`currency` 컬럼은 견적요청서에만 있는 글자 칸이다 — 회계에는 통화 개념이 없다)

### ② 사용량 과금 → **정액형 / 변동형 플래그**로
사용량을 계산하려면 단가·사용량·검침일·구간요금을 다 들어야 한다.
그건 청구 시스템이 아니라 **과금 시스템**이다. 필요한 건 그게 아니라
**"이번 달은 얼마였고, 냈나"** 뿐이다.

| | 정액형 | 변동형 |
|---|---|---|
| 규칙의 금액 | 확정 금액 | **예상액**(참고값) |
| 회차 발행 | 그 금액으로 바로 | **금액을 반드시 확인** (기본값 = 직전 회차 금액) |
| 놓친 회차 **일괄** | 그대로 | **막는다** |
| 월 환산 요약 | 정확 | "예상 기준" 표시 |

⚠ **일괄 발행을 막아야 하는 이유**: 지금 일괄은 규칙의 `supply_amount` 를 회차마다
  그대로 찍는다(`routes/recurring-invoices.js:302~`). 변동형에 이게 돌면
  **석 달치가 전부 같은, 그것도 틀린 금액**으로 만들어진다. 세금계산서라 되돌리기 번거롭다.

- 추적성은 그대로다. 청구서 → 미수금 → 입금 매칭 흐름은 동일하고,
  언제·얼마를 냈는지는 `invoice_matches` 와 거래에 남는다. 바뀌는 건 **금액의 출처**뿐.
- **정기입금·정기지급 양쪽에** 넣는다. 변동형은 지급 쪽이 더 흔하다
  (전기·수도·통신·클라우드 사용료).
- 변동형에서는 **'기입금/기지급 처리'가 주력 버튼**이 된다 — 자동이체로 이미 빠진 뒤
  고지서를 보고 기록하는 순서라서. 그 버튼은 이미 금액을 묻는다.

작업 크기: 컬럼 하나(`amount_mode`) · 칩 하나 · 발행 확인창의 금액 칸 · 일괄에서 제외.

## 지금까지 나온 할 일 (2차까지 — 착수 전)

⚠ 순서의 기준: **틀린 숫자가 남는 것 > 불편한 것.**
   불편은 손이 더 가는 것으로 끝나지만, 틀린 숫자는 쌓이고 나중에 되돌리기 어렵다.

| 우선 | 할 일 | 크기 | 왜 |
|---|---|---|---|
| **1** | **계좌 간 이체 (통장 → 카드)** | 중간 | **장부가 틀리는 유일한 항목.** 지금은 신용카드 대금을 지출로 한 건 더 만들면 비용이 두 번 잡히고, 안 만들면 통장 잔액이 실제보다 많다. 소모품·비품을 카드로 사는 건 매일 있는 일이라 **틀린 금액이 계속 쌓인다** |
| 2 | **정액형/변동형 플래그** (+발행 시 금액 확인, 일괄에서 제외) | 작음 | 틀린 금액의 계산서가 나갈 위험을 막는다 |
| 3 | **수주 복제** | 작음 | "동일·유사 제품 반복 수주"가 시나리오에 직접 적혀 있다 |
| 4 | **법인카드 사용 기록부** | 작음 | 데이터는 이미 다 있다. 이름 붙은 보고서 하나면 된다 (1번을 하면 카드 사용·결제가 한 화면에서 맞아떨어진다 — 같이 하면 싸다) |
| 5 | **첨부 종류 고르기** | 아주 작음 | 지금은 올린 자리에 따라 종류가 박혀 나중에 파일명으로 뒤져야 한다 |

### 보류
- **착수계·중간보고·완료보고 양식** — 발주처마다 양식이 다르다. 실물 한 장 받으면 그때.
  (견적요청서를 실양식 나올 때까지 미뤄둔 것과 같은 이유)
- **설비 자산 처리 자동화** — 지금도 계정과목을 직접 고르면 된다. 설비 대장을 안 쓰시므로 낮음.
- **용역 작업량 기반 계산(단가×수량)** — C 지만, 지금은 금액을 직접 넣어 우회된다.
  실제로 시간·일자로 정산하는 인력이 몇 명인지 보고 정한다.
- **고정자산 임대 구분 / 차입 유형 구분 / 비정형 상환약정 / 용역 지급시점** — 전부 칸 하나씩.
  해당 건이 실제로 생겼을 때 함께 넣는 편이 낫다(미리 넣으면 안 쓰는 칸만 는다).

### 여쭤볼 것
- **유지보수 / 라이선스 / 사용료 유형 구분** — 유형으로 나누면 "라이선스 매출 연간 얼마"가
  집계된다. **그 숫자를 보고 싶어 하시는지**에 달렸다. 아니면 칸만 하나 는다.
- **체크카드를 카드 계좌로 잡고 계신지** — 체크카드는 쓴 즉시 통장에서 빠지므로
  **통장 계좌의 지출**로 다는 것이 맞다. 카드 계좌로 잡아 두면 1번(이체)이 필요 없는데도
  결제일 예측이 붙어 자금일보가 어긋난다.

### 9. 소모품·비품·행정수수료 — 현금/카드 ⚠ 이번 묶음에서 제일 큼

| 구분 | 항목 | 근거 / 메모 |
|---|---|---|
| A | 현금·**체크카드** 결제 | 쓴 즉시 통장에서 빠지므로 지출 한 건이면 끝 |
| A | **자금일보의 카드 예측** | 이미 정확하다. 카드 사용액을 결제일에 결제계좌에서 나가는 한 건으로 세우고, 이미 빠진 건은 다시 안 센다 (`lib/cashReport.js:269~`) |
| **C** | **신용카드 대금 결제 — 실제 장부** | 아래 |

⚠ **이중차감이 실제로 일어날 수 있다.**
   - 계좌 잔액은 `기초 + 입금 − 지출` 로만 계산한다 (`routes/accounts.js:29`)
   - **계좌 간 이체 기능이 아예 없다** — 코드에 미구현임이 적혀 있다
     (`routes/transactions.js:27` "계좌 이체를 도입하면 전용 경로에서 처리하고…")

   그래서 신용카드를 쓰면:
   - 카드 계좌에 지출을 달면 → 카드 잔액만 마이너스로 쌓이고 통장은 그대로 **(맞음)**
   - 결제일에 통장에서 빠진 것을 기록하려면 **지출을 한 건 더** 만드는 수밖에 없다
     → **비용이 두 번 잡힌다**
   - 안 만들면 **통장 잔액이 실제보다 많게** 남는다

   즉 **예측은 맞는데 장부가 안 맞는 상태**다.
   필요한 것은 **계좌 간 이체**(통장 → 카드, 비용 아님)다.
