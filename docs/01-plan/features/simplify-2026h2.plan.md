# 단순화 리뉴얼 (2026 하반기) — 계획

작성 2026-09-15. 근거: 알찬회계(rcount.kr) 도움말 조사 + 우리 코드 전수 조사 + 운영 데이터 실측(읽기만).

## 왜 하나

돈 하나를 **청구서 → 거래 → 매칭 → 전표 → 회차** 다섯 겹으로 다룬다. 겹마다 이중 계상을 막는
코드와 화면이 붙어, 돈을 적는 길이 15가지가 넘고 들어온 돈을 보는 곳이 6곳이다.
정기 기능은 회차·last_generated·소급·기입금을 **기억**하려다 사고가 났다
(소급 청구 폭주 7/20, fowin 중복 73건 8/27, 완납 건 회차 부활 9/10).

지금까지의 검토는 "이 코드에 버그가 있나"만 봤다. 이번부터 단계마다 **"이게 제품을 더 어렵게 만드나"**를 같이 본다.

## 목표 구조 (사용자 구상 2026-09-15)

**손에 든 것으로 고른다.**

| 방향 | 방법 |
|---|---|
| 입금 | 입금전표 · 세금계산서 발행 → 입금 처리 · 반복거래에서 가져오기 |
| 출금 | 품의서/결의서 → 출금 처리 · 출금전표 · 세금계산서 수취 → 출금 처리 · 반복거래에서 가져오기 |
| 대체 | 대체전표 (돈이 안 움직임 — 입금·출금 밖에 둔다) |

입출금 메뉴는 **반복거래 / 세금계산서 / 입출금(거래내역+등록) / 카드대금 / 내부이체 / 급여·임금** 여섯.

**2단계에 같이 할 것** (1단계 복잡도 검토에서 넘어옴)
- 첫 안내(WelcomeWizard)의 소개·완료 단계를 빼고 메뉴 고르기 한 장만 남긴다. 소개의 "정기 거래 … 회차가 자동"은
  반복거래 전환 뒤 틀린 말이 되고, 완료의 "다음은 기초 자료"는 홈 카드와 같은 말이다.
- 4단계 설계 때 '마감'이 몇 가지 뜻으로 쓰이는지(월 마감 잠금·집계 마감일·회기 마감) 한 표로 정리한다.

## 확정된 결정

- 사업자번호는 회사 정보에서 바꿀 수 있다(비울 수는 없음, 감사 기록). 처음엔 잠금으로 설계했다가 사용자 결정으로 바꿨다.
- fowin 매출 반복 20건도 반복거래로 옮기고, 매출 반복은 세금계산서(미수금)로 만든다.
- 회기는 알찬회계처럼 DB를 나누지 않는다 — 해를 넘는 미수금·계약·원장이 끊긴다.
- 반복거래는 회차를 저장하지 않는다. "이번 달 만든 것 있음"은 데이터에서 계산한다.
- 문서 복사는 연결 정보(원본 품의·지출 거래·세금계산서)·승인 상태·날짜를 복사하지 않는다.
- 세 경로가 같은 돈에서 만나므로 중복 가드(open_invoice·dup_txn·수취 시 기존 출금 연결)는 유지한다.

5. 수정 → 배포 게이트(백업·배포·헬스·시나리오·로그·푸시)
